# HA-SODQN 两阶段实施与实验执行 Plan（2026-07-26）

## 1. 文档职责

本文件是 `docs/HA-SODQN_设计说明与实验方案.docx` 在当前仓库上的可执行实施计划，供 Codex CLI agent 连续完成两个阶段：

1. **阶段一：代码支撑**——在现有顺序 Online DQN 基础上建立 Plan 1 静态历史档案、P1C/P1F 可见控制、DHOA/OWP、混合采样、审计、恢复和分析能力。
2. **阶段二：实验执行**——在阶段一验收通过后，按预注册顺序构建 manifest、调用实验、持续检查运行状态、恢复失败运行、严格验收并形成筛选与正式比较结果。

阶段一通过前不得启动正式矩阵。阶段二的职责不只是发出命令，还包括确认实验持续推进、发现停滞或失败、执行安全恢复、核对完整性并完成阶段报告。

本 Plan 不要求修改 `docs/plan0721.md`。若后续需要把 HA-SODQN 状态纳入总 Plan，应先向用户说明拟修改内容并获得允许。

## 3. 冻结研究协议

### 3.1 两类 replay 的生命周期

- **ORB**：当前 HA-SODQN 运行中的 Online Replay Buffer，容量 5,000，跨 stage 持续 FIFO，不在场景切换时清空。CONT-FIFO 是关闭全部 HOA 能力后的直接基线。
- **HOA**：Plan 1 Q1 静态只读档案，运行期间不可写、不可被当前 trajectory 替换。
- **OWP**：RAND/COV/CQ/CQA 在每个 stage 从当前可见 HOA 构建的固定工作池；stage 内冻结，下一 stage 重新构建。
- **DHOA**：不建立固定 OWP，直接从当前可见 HOA 抽样。

### 3.2 Archive Visibility

- `P1C`：stage k 只能看到顺序中 stage 1 到 k-1 对应场景的 Plan 1 Q1 数据；当前与未来场景必须屏蔽。
- `P1F`：从 T1 起可看到四场景全部 Plan 1 Q1 数据；这是允许当前/未来数据的全历史对照，不能用于证明严格因果历史利用。
- P1C T1 的可见 HOA 必须为空，所有 P1C 方法自动退化为纯 Online；不允许用重复样本填充 offline quota。

### 3.3 训练起点与预算

- 每条运行从 Plan 1 对应 training seed 的 **episode-0 resumable checkpoint** 初始化，恢复模型、target、optimizer、epsilon、计数器和 RNG，但 ORB 为空。
- 对每个 Order，应使用该 Order 首场景对应的 Plan 1 episode-0 checkpoint 建立可审计 initial-state catalog；不得从 episode-100 parent 再追加一个 T1。
- T1–T4 每个 stage 都实际训练 100 episodes，总计 400 episodes/run。
- 每个 episode 3,600 simulation steps，action interval 10，batch size 64，learning start 1,000，buffer size 5,000，update rate 1，target interval 10；模型、optimizer、gamma、epsilon 和 gradient clip 沿用 b100 顺序配置。
- 加入 Offline 数据不得增加总 gradient update 数；同一 decision 最多执行原协议规定的一次更新。
- SUMO 继续使用 `fixed_default`，training seeds 为 0–4。

### 3.4 混合更新

- Offline ratio 表示每次 gradient update 的离线样本占比：R25=16/64、R50=32/64、R75=48/64。
- 分别计算 `loss_online` 与 `loss_offline`，总损失使用：
  `loss = (1-rho) * loss_online + rho * loss_offline`。
- 两类 transition 都使用当前 online/target network 重算 TD target，不读取或保存 Plan 1 的旧 Q target。
- P1C T1、HOA 为空或统一 warm-up 期间使用 64/64 Online batch，并记录实际 ratio=0。
- CQA 需要在线窗口时，所有带 HOA 的方法都采用相同 `alignment_warmup_episodes=10`：warm-up 仍正常 Online 更新，但直到 warm-up 完成后才启用 Offline 混合，避免 CQA 独享额外交互或不同启动条件。

### 3.5 随机性隔离

新增能力不能因 OWP 构建或 Offline 抽样额外消耗动作探索 RNG。至少拆分并记录：

- model/action RNG：由 `training_seed` 控制；
- online replay sampler RNG：由 training seed 确定性派生；
- HOA/OWP sampler RNG：由 training seed 确定性派生且与 online/action RNG 独立；
- evaluation RNG：沿用现有隔离机制。

派生公式应固定在配置/manifest 中，不依赖 Python `hash()`。checkpoint/resume 必须保存全部新增 RNG 状态。

### 3.6 Plan 1 behavior seed 规则

先执行同 seed trajectory 重复性审计。若新 T1 与 Plan 1 同 training seed、同首场景 trajectory 可逐 transition 复现，则 HA 运行默认从 HOA 中排除 `behavior_training_seed == training_seed`，使用其余四个 behavior seeds，避免把当前运行的确定性副本作为“外部历史”；若不能逐 transition 复现，则保留全部五个 seeds。

无论审计结果如何，规则必须：

- 在代码和配置中显式表达；
- 对同一 Order/seed 的所有 Method/Ratio/Archive 配对保持一致；
- 写入 archive manifest、run manifest 与诊断结果；
- 不得由某个方法自行改变。

### 3.7 OWP v1 默认参数

首次实现使用可配置默认值，不在方法代码中硬编码：

- `owp_capacity=5000`，与 ORB 容量一致；
- RAND：从可见 HOA 无放回确定性抽样；
- COV：在 scene/behavior-seed 来源平衡基础上，按 state、phase、action 的确定性 coverage descriptor/分层单元分配配额，抑制高频单元支配并保留稀有单元；
- CQ：保持 COV 配额，在 coverage 单元内部按可稳定关联的质量分数优先选择；v1 优先使用 episode mean/return 与局部 reward 统计，不引入无法从现有数据验证的外部评分；
- CQA：OWP 的 75% 使用 CQ 全局保持部分，25% 使用与当前 stage 前 10 episodes 状态分布最接近的对齐部分；P1C 检索范围仍只能是已解锁场景。

Coverage、Quality、Alignment 的具体数学定义、归一化、tie-break 和版本号必须写入生成的 OWP manifest。若性能/内存 profile 证明上述实现不可行，可在不改变方法含义的前提下采用更高效的确定性实现，并在配置与报告中说明。

## 4. 阶段一：代码支撑

### 4.1 A0——仓库与数据审计

1. 检查工作树，保留用户已有改动，不提交生成数据、缓存或大型结果。
2. 验证四个 Plan 2 Q1 manifest、source index、Plan 1 shard SHA-256、episode 范围、state/action 维度和场景语义哈希。
3. 建立 HA-SODQN archive root manifest：引用四个 Q1 manifest，不复制原始 NPZ；记录 dataset ID、manifest hash、source root、四场景 transition 数和 seed 规则。
4. 建立 episode-0 initial-state catalog：O1–O4 × seeds 0–4，共 20 个逻辑起点；同 seed 不同首场景的模型/optimizer/RNG 是否等价要审计并记录，运行时仍引用实际首场景来源。
5. 对现有 b100 分析执行只读摘要，确认 O2 为 pilot 顺序，并记录依据。

**A0 验收**：数据源可只读加载、哈希通过、20 个初始状态可恢复、没有复制或修改 Plan 1 trajectory。

### 4.2 A1——统一静态档案接口

新增或扩展只读数据层，使其能够：

- 从 archive root manifest 按 network、behavior seed、episode、transition ID 查询；
- 返回与顺序 DQN 兼容的 observation/action/reward/next observation/terminated/truncated；
- 保留 network、behavior seed、run ID、episode、decision step、shard hash 和稳定 transition ID；
- 创建不复制底层数组的 visible view；
- 提供确定性抽样、来源统计、unique coverage 和 RNG state；
- 在加载时验证 observation dim=16、action dim=8 及语义哈希一致。

优先复用 `dataset/offline_trajectory_dataset.py` 的 schema 校验和只读加载逻辑，避免再实现一套含义相近的数据验证器；如需扩展其 batch/provenance 接口，应保持 Plan 2 行为兼容。

### 4.3 A2——P1C/P1F Visibility Controller

实现面向任意有序 network list 的控制器：

- 输入 archive mode、ordered networks、stage index；
- 输出 visible、masked-current、masked-future network 集合及 transition 数；
- P1C 使用 `ordered_networks[:stage_index-1]`；
- P1F 使用 archive 中全部 network；
- 对不在顺序中的 network、重复 network、越界 stage 立即失败；
- 生成 stage visibility manifest 和 digest，供 checkpoint/resume 与 validator 核对。

### 4.4 A3——DHOA 与 OWP Builder

实现 `DHOA/RAND/COV/CQ/CQA` 五种方法，使用统一接口：

- 输入 visible HOA、stage identity、method config、独立 RNG 和可选 warm-up descriptor；
- 输出可采样 view 或冻结 OWP，以及 manifest、统计和 digest；
- RAND/COV/CQ/CQA 每 stage 只构建一次；resume 时不能无记录地重建为不同集合；
- DHOA 保持面向完整 visible HOA，不伪装成容量无限的 OWP；
- OWP manifest 至少记录容量、候选数、选中数、每 scene/seed/episode/action/coverage 单元组成、quality 分布、alignment 分布、unique transition IDs digest 和构建耗时。

### 4.5 A4——ORB 与 Mixed Batch Sampler

- 保持一个跨 stage 的 FIFO ORB，容量 5,000；当前 transition 只写 ORB。
- 新增 mixed sampler，严格生成 batch 64 和 R25/R50/R75 配额。
- Online/Offline 两支 loss 分开计算后组合；记录两支样本 ID、loss、Q/target 稳定性与实际 ratio。
- learning-start 与 update readiness 不能依赖 HOA 伪造 Online warm-up；ORB 未达到在线训练门槛时不更新。
- P1C T1/空 HOA/前 10 episode warm-up 自动全 Online。
- Offline sampling 不改变动作 RNG；checkpoint 保存 ORB、HOA/OWP identity、sampler RNG 与累计采样统计。

### 4.6 A5——顺序运行、配置与 manifest

在现有 `sequential.cli` / runtime 体系中增加明确的 HA-SODQN 命令与身份，至少支持：

- archive mode：`none/P1C/P1F`；
- method：`DHOA/RAND/COV/CQ/CQA`；
- ratio：`0/0.25/0.50/0.75`；
- ordered networks、stage episodes、training seed；
- archive root manifest、initial-state catalog；
- OWP capacity、coverage/quality/alignment 版本与 warm-up；
- pilot/formal manifest 构建、validate、launch、status、resume-failed、audit、analyze。

配置建议新增 `configs/sequential/ha_sodqn_b100.yml`，不得把 HA 参数塞入原有 `plan34_b100.yml` 或改变已有正式 manifest 的 digest 语义。

logical run identity 至少包含 Archive、Method、Ratio、Order、Seed；CONT-FIFO 单独标识。相同 logical identity 的失败恢复使用不可变 attempt/resume 链，不覆盖前驱目录。

### 4.7 A6——阶段评估与审计记录

复用现有独立 evaluator，每个 stage 结束后只评估已见场景，生成严格下三角：T1=1、T2=2、T3=3、T4=4 个场景。

每 episode 或每次更新的结构化记录至少覆盖：

- archive mode、method、ratio、order、training seed、stage/current network；
- visible/masked networks、HOA candidate count、OWP digest/capacity/source composition；
- ORB size/composition；
- requested 与 actual online/offline counts/ratio；
- offline source scene/seed/episode 贡献、unique coverage、reuse count；
- online/offline/total loss，必要的 Q/target finite 检查；
- gradient update、epsilon、target update 和 RNG identity；
- stage checkpoint、evaluation aliases 和 lower-triangle cells。

P1C validator 必须逐个离线样本检查来源；发现当前或未来 network 时将 run 判为无效，而不是只写 warning。

### 4.8 A7——严格验证与分析支持

新增 validator/analysis，至少能够生成：

- run-level 完整性和配置/hash 审计；
- P1C leakage audit；
- update-budget fairness audit；
- OWP determinism/freeze audit；
- actual ratio 与来源组成表；
- adaptation curve/AULC（前 20、前 50、全 100）；
- reward、queue、delay、real delay、throughput、travel time 下三角矩阵；
- absolute/relative forgetting、retention ratio、average/worst-case forgetting；
- 同 Order/seed 配对比较与 bootstrap/sign-flip 结果；
- pilot 候选筛选表和正式跨 Order 汇总图。

分析器只接收 validator 通过的 run-list，默认拒绝缺失、重复、配置不一致、泄漏或 incomplete runs；开发 smoke 不得混入科研结果。

### 4.9 A8——测试与最小运行验证

4. 预算测试：CONT 与 R25/R50/R75 的 gradient update 数一致；总 batch 恒为 64。
5. 真实 SUMO 组合 smoke：使用一个缩短 stage 预算的 manifest 覆盖 CONT、P1C-DHOA-R50、P1C-CQA-R50 和 P1F-DHOA-R50，验证四类关键分支，不分别执行重复 smoke。

### 4.10 阶段性 Git 管理与远端交付

- 对产生 tracked source/config/test 修改的可独立验收模块或紧密相关模块组，完成最小验证后必须使用中文提交信息执行 Git commit；不为没有 tracked 修改的审计步骤制造空 commit。

- 每个阶段性 commit 完成后必须立即 push 到当前远端分支，并记录 remote、branch 和 commit SHA；只有 commit 与 push 均成功，该代码模块才视为完成。
- push 失败时先检查远端、分支、认证和网络；需要权限时按执行环境流程请求用户批准。不得通过 force push、改写远端历史或跳过远端交付继续宣称模块完成。

- 阶段二正式 manifest 必须记录并校验该冻结 SHA；不得使用仅存在于本地、尚未 push 的代码启动正式实验。
- 不擅自创建 PR，不使用 `git push --force`，不修改或覆盖用户已有提交。

## 5. 阶段二：实验调用、运行推进与确认

### 5.1 执行原则

- 只使用阶段一冻结并通过验收的 commit、config 和 archive manifest 构建正式运行。
- 阶段一冻结 commit 必须已经 push 到当前远端分支，正式 manifest 同时记录 git commit、remote 和 branch。
- 每一波先 build/validate manifest，再 launch；manifest、config hash、git commit 和 output root 不可在波次中途修改。
- 启动后持续检查 logical status、attempt 状态、最后进度时间、CPU/内存/磁盘、SUMO 残留和评估队列；不能把“进程存在”视为正常推进。
- 对失败或外部中断运行使用既有 checkpoint 和 `resume-failed` 语义创建后继 attempt；保留前驱并在 recovery ledger 中记录。
- 不因单个结果差而重跑或替换 seed；只有工程失败、证据损坏或 validator 拒绝才允许恢复/重跑。
- 每个 E 阶段必须在 validator 100% 通过后才能进入依赖其科研结果的下一 E 阶段；同一 E 阶段内部采用滚动调度，不把 8 个一组的人为批次当作必须等待的同步屏障。
- 正式训练默认固定 `max_child_concurrency=8`，尽可能持续占满 8 个训练槽；某个 logical run 完成后立即调度同一 E 阶段的下一个待运行单元。
- 只有出现可复现的内存不足、磁盘风险、SUMO/TraCI 资源冲突、系统持续过载或运行正确性问题时才允许临时降到 6 或 4，并必须记录证据、影响和恢复到 8 并行的条件。

### 5.2 E0——链路验收与基线冻结

使用阶段一的最终组合 smoke 和唯一完整运行完成链路确认：

- `P1C-DHOA-R50-O2-SD0`。

确认 episode-0 起点、四个 100-episode stage、T1 P1C 退化、实际混合比例、更新公平、下三角评估和恢复链路；CONT-FIFO 关闭路径由同一最终代码的组合 smoke 覆盖。E0 通过且冻结 commit 已 push 后，不再为改善科研指标修改训练语义。

### 5.3 E1——O2/seed0 固定 Ratio 五方法筛选

主设置为 P1C，运行下列矩阵并复用身份完全一致的 E0 DHOA-R50；CONT-FIFO 在本阶段首次执行正式 100×4 运行：

| Ratio | Methods |
| --- | --- |
| R25 | DHOA、RAND、COV、CQ、CQA |
| R50 | DHOA、RAND、COV、CQ、CQA |
| R75 | DHOA、RAND、COV、CQ、CQA |

规模为 15 个 P1C 配置 + 1 个 CONT，共 16 个逻辑运行；已完成且身份完全一致的 E0 P1C-DHOA-R50 运行不得重复计算。整个 E1 manifest 以 `max_child_concurrency=8` 启动，形成最多 8 个同时训练的 rolling queue，而不是手工等待第一组 8 个全部结束后再启动第二组。

E1 重点检查：

- T2 第一次历史利用；
- T3 多历史来源时的来源支配、coverage 和 quality 差异；
- T4 average/worst forgetting；
- R25/R50/R75 当前适应与历史保持的权衡；
- CQA alignment 部分是否实际选到不同于 CQ 的样本。

### 5.4 E2——候选配置多 seed 验证

对 E1 结果使用预注册筛选规则：

1. CONT-FIFO 必选；
2. DHOA、CQ、CQA 各保留一个代表 ratio；
3. 候选相对 CONT 的当前场景 normalized travel-time AULC 退化原则上不得超过 5%，同时应改善 average forgetting、worst forgetting 或 retention 中至少一项；
4. RAND/COV 只有在表现明显不同、形成必要消融或优于相邻方法时才额外保留；
5. 总候选控制在 3–5 个配置（含 CONT）。

在 O2 上补齐 training seeds 0–4。选择报告必须列出全部 E1 配置，不得只展示入选方法。

### 5.5 E3——P1C 与 P1F 对照

- 从 E2 选出一个代表 ratio；优先 R50，除非 E1/E2 明确支持另一个比例。
- 在 O2 上运行 P1F 的 DHOA、RAND、COV、CQ、CQA，先 seed0 验证，再补齐 seeds 0–4。
- 与相同 Method/Ratio/Order/Seed 的 P1C 成对比较。
- 明确报告 P1F T1 已使用当前/未来场景数据，不能把 P1F 结果解释为无泄漏因果实验。

### 5.6 E4——跨 Order 正式验证

主正式集合默认包括：

- CONT-FIFO；
- P1C-DHOA 的 E2 代表 ratio；
- P1C-CQ 的 E2 代表 ratio；
- P1C-CQA 的 E2 代表 ratio；
- 可选 P1F-CQA 代表配置，作为全历史上限参考。

对 O1–O4、training seeds 0–4 运行完整 100×4 stage。已在 O2 完成且身份一致的运行直接复用；不得为统一目录而重复训练。

核心比较以同 Order/seed 配对为单位，报告：

- 当前场景 AULC 与 stage-final 性能；
- 每个历史场景的 absolute/relative forgetting 与 retention；
- average seen-scene performance、average forgetting、worst-case forgetting；
- 方法 × Order 交互与 seed 方差；
- 实际 offline ratio、unique coverage、来源组成、loss/Q 稳定性；
- P1C 与 P1F 的收益差及其未来信息边界。

### 5.7 运行监控与恢复检查表

Agent 在每个运行波次中循环执行以下工作，直到该波次完成或出现需要用户决策的真实阻塞：

1. `status` 汇总 planned/running/completed/failed/stale 数量；
2. 正常情况下保持 8 个 running child；有空闲 slot 且存在 planned/recoverable run 时立即补位；
3. 检查 running attempt 的最后 journal/episode/decision 时间是否持续更新；
4. 检查系统负载、可用内存、当前磁盘和预计剩余空间；
5. 核对 launcher 与 SUMO 子进程数量，识别 orphan 和超过 8 个 child 的错误调度；
6. 对完成运行立即执行轻量增量 validator，尽早发现 schema、ratio、leak 或 evaluation 缺失；完整矩阵 validator/聚合在当前 E 阶段所有 logical runs 完成后执行；
7. 对失败运行解析 stderr/current_state/resume_pointer，确认可恢复点后使用正式 resume 入口；恢复运行占用同一组 8 个训练槽；
8. 更新 wave ledger：logical ID、attempt、开始/结束时间、状态、恢复关系、validator 结果；
9. 每完成一个 E 阶段生成阶段摘要，再进入依赖其结果的下一阶段。

不能通过删除失败目录、覆盖 checkpoint、手改 completed 标志或 `--allow-incomplete` 让正式矩阵看似完成。

- E0–E4 的实际执行矩阵、复用关系和排除项均有清单；
- 所有纳入运行 validator 通过，无 P1C 当前/未来数据泄漏；

- 正式汇总不使用 `allow-incomplete`；

### 6.3 科研结论边界

最终报告至少回答：

1. 严格 P1C 下 Plan 1 静态历史是否减轻过去场景性能下降；
2. DHOA 与固定 OWP 是否有差异；
3. Coverage、Quality、Alignment 是否带来可观察增量；
4. R25/R50/R75 如何影响当前适应与历史保持；

6. 主趋势是否跨 Order 和多个 training seeds 保持。

代码可运行、单次指标改善或实验全部结束都不能单独视为科研结论成立。若方法没有优于基线，也应如实报告稳定的负结果、适用边界和机制诊断。
